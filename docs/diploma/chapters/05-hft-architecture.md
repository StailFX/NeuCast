# Глава 4. Архитектура высокочастотного слайса

> Перерабатывает `docs/highfreq/architecture.md` в академический
> формат. Раскрывает решение второго класса задач, которое в
> курсовой 2026 года было обозначено только как «перспектива
> развития».

## 4.1. Постановка задачи высокочастотного прогнозирования

Дневное прогнозирование, рассмотренное в Главе 3, оперирует на
горизонте 30 торговых дней с использованием OHLCV-агрегатов. Класс
задач «высокочастотного прогнозирования» (high-frequency
forecasting) принципиально отличается тремя характеристиками:

* **Горизонт прогноза** уменьшается до одной минуты или нескольких
  секунд — на этом масштабе классические дневные тренды и
  макроэкономические факторы практически нерелевантны;
* **Источник данных** — не агрегированные OHLCV, а полная книга
  заявок биржи (Limit Order Book, L2) с обновлениями в темпе
  поступления каждой котировки, что требует прямого подключения
  к WebSocket-API биржи и обработки ≈ 100–1 000 событий в секунду;
* **Релевантные признаки** — микроструктурные характеристики
  стакана (Order Flow Imbalance, дисбаланс глубины, спред,
  micro-цена), не вычислимые из дневных свечей.

В рамках данной работы для исследования был выбран рынок Binance
Spot — крупнейшая по обороту криптовалютная биржа, предоставляющая
бесплатный публичный WebSocket-API на уровне L2 (полная глубина
стакана) с задержкой обновления <50 миллисекунд.

## 4.2. Топология двух виртуальных серверов

Принципиальное архитектурное решение HFT-слайса — физическое
размещение сборщика данных вблизи серверов биржи. Binance Spot
размещён в дата-центре AWS в регионе Tokyo (ap-northeast-1).
Сетевая задержка от типичного европейского хостинга до Tokyo
составляет 200–250 миллисекунд, что превышает горизонт типового
изменения котировки и делает прогнозирование на 1-минутном
горизонте бессмысленным.

Для решения этой проблемы развёрнуты два сервера:

* **Финляндия (Helsinki, IP 151.245.139.21)** — публичный
  фронтальный сервер с TLS-сертификатом, обслуживающий
  пользовательский веб-сервис из Главы 2.
* **Япония (Tokyo, IP 147.45.49.40)** — серверная площадка для
  HFT-слайса, расположенная в одном с Binance дата-центре и
  обеспечивающая RTT 19 миллисекунд до Binance WebSocket-API.

Между серверами установлен зашифрованный VPN-туннель WireGuard
(UDP, ChaCha20-Poly1305 cipher) с приватной подсетью 10.99.0.0/24.
HF-эндпоинты `/api/highfreq/*` проксируются с фронтального
сервера через nginx в туннель и далее к slim-FastAPI в Tokyo.
С точки зрения пользователя браузера это выглядит как один
домен neucast.ru; двухсерверная архитектура — деталь реализации.

## 4.3. Сбор и нормализация L2-данных

Сборщик данных (`app/highfreq/ingest.py`) реализован на asyncio с
прямым подключением к Binance WebSocket-API. На каждое из трёх
исследуемых символов (BTCUSDT, ETHUSDT, BNBUSDT) поддерживается
отдельный пер-сокетовое соединение, подписанное на канал «depth»
(полные обновления книги заявок) и канал «trade» (поток сделок).

Принимаемые события группируются по 1-секундным интервалам и
нормализуются в единую табличную структуру `highfreq_ofi_1s`
(Postgres), содержащую следующие микроструктурные признаки на
каждой 1-секундной отметке:

* `microprice` — микроцена, взвешенное среднее лучших bid/ask по
  объёму на ближайших уровнях (P̄ = (P_b · V_a + P_a · V_b) /
  (V_a + V_b)), более точное прокси истинной цены, чем mid-price
  при асимметричных стаканах;
* `ofi` — Order Flow Imbalance, разница между объёмами агрессивных
  покупок и продаж за интервал;
* `depth_imb` — отношение объёмов в стакане на bid и ask на 5
  ближайших уровнях;
* `spread_bps` — спред между лучшими bid и ask в базисных пунктах;
* `trade_imb` — дисбаланс знаков сделок за интервал;
* `n_updates` — счётчик обновлений книги за интервал
  (диагностический показатель активности рынка).

Объём данных составляет приблизительно 86 400 строк в сутки на
символ; за месяц — 2.6 миллиона строк; на двух символах в каждом
дневном файле — порядка 50 МБ Parquet. Холодное хранилище — Yandex
Object Storage с retention-политикой 7 дней горячего хранения и
бессрочного холодного.

## 4.4. Конвейер построения признаков и модели

Конвейер обработки данных от сырых L2-событий до прогноза
направления цены устроен следующим образом (модули в `app/highfreq/`):

```
   [Binance WebSocket]              ingest.py            ┐
        ↓                                                │ Tokyo
   highfreq_ofi_1s (Postgres)       feature_pipeline.py │
        ↓                                                │
   1-минутные агрегаты              trainer.py            │
        ↓                                                │
   weights/highfreq/*.cbm           predictor.py         │
        ↓                                                │
   /api/highfreq/* (slim FastAPI)                        ┘
        ↓                                              ┐
   nginx + WireGuard                                   │ Helsinki
        ↓                                              │
   neucast.ru/api/highfreq/*                           ┘
```

Признаки на 1-минутной сетке формируются агрегацией 1-секундных
строк за окно бара: суммарный OFI, средний и максимальный
spread_bps, дисперсия depth_imb, среднее количество обновлений и
другие статистики. Полный список из 18 признаков фиксирован в
`app/highfreq/feature_pipeline.py` и не меняется без переобучения
модели.

## 4.5. Модель: CatBoost-классификатор направления цены

В качестве модели прогнозирования направления цены за следующую
минуту использован CatBoost-классификатор (см. §1.4 теоретической
части). Целевая переменная — индикатор «цена через 1 минуту выше
текущей», рассчитываемый по микроцене во избежание влияния
bid-ask шума.

Гиперпараметры обучения подобраны грид-поиском на отдельной
валидационной выборке:

* depth = 5 (баланс между смещением и переобучением);
* iterations = 200 с ранней остановкой по log-loss на валидации;
* learning_rate = 0.05;
* L2 регуляризация = 3.0;
* функция потерь — log-loss (бинарная классификация).

Калибровка вероятностей выполняется отдельным изотоническим
регрессором, обучаемым на out-of-sample предсказаниях из
walk-forward цикла (см. §1.8 — теоретическое обоснование выбора
изотонии при n_oos ≥ 1000).

## 4.6. Эксплуатационные механизмы безопасности

Поскольку HFT-модель встраивается в paper-trading контур
(симулированную торговлю на реальных данных), архитектура
включает несколько защитных механизмов:

* **Калибровочный гейт** — модель не принимает торговые решения,
  пока её dir_acc на out-of-sample не подтверждена нижней
  границей доверительного интервала Уилсона строго выше 0.5;
* **Anti-skill detector** — постоянно отслеживает скользящую
  винрейт-долю последних 50 закрытых сделок; если верхняя граница
  bootstrap-CI окажется ниже 0.5, модель автоматически
  переключается в режим инверсии или останавливается;
* **Event-halt** — за 15 минут до и 60 минут после крупных
  макрособытий (FOMC, NFP, CPI) торговля приостанавливается; список
  событий ведётся в `docs/highfreq/event_calendar.json`;
* **Drift detector** — KS-тест на распределении признаков с
  периодом 1 час; при критическом дрейфе (см. Гл. 6) модель
  автоматически отключается до следующей переобучения.

## 4.7. Мониторинг и наблюдаемость

Состояние HFT-слайса непрерывно мониторится через Prometheus +
Grafana. Метрики:

* `hf_ingest_rows_last_60s_total{symbol}` — счётчик принятых
  событий за минуту, индикатор живости сборщика;
* `hf_predictor_age_seconds{symbol}` — время с последней успешной
  прогностической операции;
* `hf_paper_trader_open_positions{symbol}` — количество открытых
  позиций в текущий момент;
* `hf_drift_severity{symbol}` — тройная категориальная переменная
  (ok / warn / high) состояния KS-теста;
* `neucast_hf_*_last_success_timestamp_seconds` — heartbeat-метрики
  для всех cron-задач (трейнер, архивация L2, paper-trades
  бэкап).

Настроены 5 правил оповещения в Grafana с уведомлениями в
Telegram-бота: stale ingest, stale trainer, anti-skill detected,
high drift, l2-archive-stale.

## 4.8. Сравнение архитектурных решений Daily и HFT

| параметр | Daily-сервис (Гл. 2) | HFT-слайс (эта глава) |
|----------|----------------------|------------------------|
| Источник данных | Yahoo Finance API (REST) | Binance WebSocket (push) |
| Темп обновления данных | дневной | непрерывный, ~100 events/sec |
| Типичный объём данных | ~3 KB/день/тикер | ~86 400 строк/день/тикер |
| Горизонт прогноза | 30 торговых дней | 1 минута |
| Используемые признаки | OHLCV + TI + макро | 18 микроструктурных |
| Модель | TCN + CatBoost + foundation | CatBoost (с calibration) |
| Хранилище | PostgreSQL (метаданные) | PostgreSQL (горячее) + S3 (холодное) |
| Расположение сервера | Финляндия (Helsinki) | Япония (Tokyo) |
| Latency-budget | секунды на запрос | <100 миллисекунд на тик |
| Использование Celery | да (синхр. невозможна) | нет (всё в asyncio) |

Несмотря на принципиально разные требования и архитектуры, оба
сервиса используют единую кодовую базу для обмена данными между
backend-ами (через nginx-проксирование) и единую систему
наблюдаемости (Prometheus / Grafana / Telegram).
